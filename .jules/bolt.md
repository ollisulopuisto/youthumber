# Bolt's Journal - Performance Learnings

## 2026-11-01 - Fast image mask compositing with typed array bulk cloning
**Learning:** During speaker mask refinement (threshold / choke slider adjustments), `applyMaskToImageData` executes repeatedly over full-HD RGBA buffers (2,073,600 pixels). Manually indexing and copying each RGB channel per pixel in JavaScript (`output[idx] = sourceRgba[idx]`, etc.) causes over 6.2 million array read/write operations in the interpreter loop. Initializing `output = new Uint8ClampedArray(sourceRgba)` lets the engine delegate RGB copying to a single native bulk memory copy (memcpy), allowing the JS loop to only modify the alpha channel (`idx + 3`). Additionally, fast-pathing the common case (`opacity === 1` and `sourceAlpha === 255`) skips floating-point division and rounding, dropping loop execution time from ~50ms to ~32ms per full-HD frame (~36% faster).
**Action:** When performing pixel-manipulation passes that modify only a subset of channels (such as alpha masking or channel tinting), use bulk typed-array cloning or 32-bit views before looping, rather than copying all channels element-by-element in JS.

## 2026-11-03 - Pointer progression and row-offset hoisting in alpha hit-testing
**Learning:** `alphaMapFor` generates a 512x512 downscaled alpha map for per-pixel pointer hit testing. Calculating `pixels[i * 4 + 3]` per pixel performs 262k multiplications per map extraction. Stepping linearly with `let i = 0, idx = 3; i < alpha.length; i++, idx += 4` drops map extraction time from ~176ms to ~98ms per 200 maps (~44% faster). Additionally, in `isMapTransparent`, hoisting `rowOffset = py * width` out of the inner loop over `px` removes repeated row multiplications on every tested cursor coordinate, reducing hit-test evaluation time by ~14%.
**Action:** In pixel extraction and 2D grid hit-testing loops, prefer linear index pointer progression and hoist row-offset calculations out of nested column loops.

## 2026-11-03 - Pre-projecting aspect coordinates and typed array flattening in 2D Voronoi shader
**Learning:** In procedural generation shaders (`procgen.js` Voronoi / Facets), computing distances across 28–47 sites per pixel in a 640×360 pass (230,400 pixels) causes over 8.7 million iterations of `(s.x - u) * aspect` multiplications and object property accesses. Pre-scaling site x coordinates by aspect up front (`siteSx = new Float64Array(n)`) and storing sites in flat typed arrays allows calculating `uAspect = u * aspect` once per pixel and directly evaluating `dx = siteSx[i] - uAspect`. This reduced average 1280×720 render time from 77.43ms to 61.50ms (~20.6% faster).
**Action:** When evaluating geometric distance fields against point sets across image pixels, pre-scale coordinate axes to eliminate inner-loop aspect ratio multiplications and pack point attributes into flat typed arrays.

## 2026-11-04 - Scanline y-distance hoisting in 2D Voronoi shader
**Learning:** Even after flattening site arrays in `voronoi` (`procgen.js`), computing vertical distance per site `dy = siteY[i] - v` and squaring it (`dy * dy`) inside the per-pixel shade function still resulted in 8.7M+ redundant floating-point multiplications per 640×360 pass, since `v` remains identical across all columns of a row. Pre-allocating `dy2 = new Float64Array(n)` and updating it only when `v !== lastV` (once per row) eliminated $n \times (lw - 1)$ multiplications and subtractions, reducing Full HD render time from ~49.2ms to ~40.3ms (~18% faster).
**Action:** In 2D per-pixel procedural shaders where a coordinate dimension ($v$ or $u$) is constant across a raster scanline or chunk, precompute axis-specific distances into a typed array at the row boundary rather than re-evaluating them at every individual pixel.
